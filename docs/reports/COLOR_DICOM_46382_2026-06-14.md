## 2. Root cause — there was no "broken colour decode"

The premise ("colored DICOM not decoding") did not match the data. The colour the
user (and a reference viewer) sees comes from two standard mechanisms the FAST
viewer was ignoring, plus one Siemens-proprietary one:

1. **Series 21 / 22 — embedded Palette Colour LUT on a MONOCHROME map.** These
   are grayscale parametric maps (WO, TTP/time-to-peak) that *embed* a 4096-entry
   16-bit Red/Green/Blue Palette Colour LUT (+ `PaletteColorLUTUID`). The scanner
   ships the exact pseudo-colour map; reference viewers apply it. AI-PACS applied
   grayscale window/level and ignored the LUT → grayscale.
2. **Series 100 / 101 #5–6 — chart in a DICOM overlay plane.** These are Siemens
   `CSA BLACK IMAGE` secondary captures: PixelData is deliberately all-zero and the
   visible content — the **"Result Table 1 / Mean Curve" ROI table** (patient name,
   time points, ROI Mean/SDev/Area) — lives in overlay group **(6000,3000) type G**
   (Graphics). AI-PACS rendered only the black pixels → blank slice.
3. **Siemens MedCom Object Graphics** `(0029,1210) OOG` — a private vector blob
   that a full syngo viewer renders (can be colour). Proprietary; out of scope.

## 3. Fix — standards-based colour + overlay (FAST viewer)

Two new isolated modules + minimal hooks in `modules/viewer/fast/pydicom_2d_backend.py`.
A plain grayscale CT/MR is unchanged (only a couple of tag look-ups; the no-overlay
mono path stays the fast `Format_Grayscale8` build).

### `dicom_color.py` — `decode_color_for_display(ds, arr)` → RGB uint8 or None
- **RGB** → passthrough.
- **YBR_FULL / YBR_FULL_422** → `convert_color_space(...,'RGB')`.
- **PALETTE COLOR** → `apply_color_lut`.
- **Embedded Palette Colour LUT on MONOCHROME** (the 21/22 case) → `apply_color_lut`.
- 16-bit colour / 16-bit LUT entries scaled to 8-bit.
- `_decode_slice` routes through it (replacing the old `samples>=3`-only RGB branch
  that had no YBR/palette support); `get_frame` keys colour on the decoded array
  being 3-D, so PALETTE / embedded-palette (SamplesPerPixel==1) still take the RGB
  path and **window/level never destroys colour**.
- Gates: `AIPACS_DICOM_COLOR`, `AIPACS_DICOM_PALETTE_ON_MONO` (both default on).

### `dicom_overlay.py` — `extract_overlay_mask(ds, rows, cols)` → HxW 0/1 or None
- Reads all overlay groups 6000–601E via `pydicom get_overlay_array`, combines them,
  places sub-size/offset overlays at the Overlay Origin.
- `_decode_slice` extracts once (only genuine overlays cached, bounded); `get_frame`
  composites lit pixels in a highlight colour (`AIPACS_DICOM_OVERLAY_COLOR`, default
  green) via `_apply_overlay`. Standard overlays are 1-bit → single colour.
- Gate: `AIPACS_DICOM_OVERLAY` (default on).

## 4. What is now supported

- RGB, YBR_FULL, YBR_FULL_422 (uncompressed; compressed already de-planarised by the
  decode handlers), PALETTE COLOR, and an **embedded Palette Colour LUT on a
  MONOCHROME image** → rendered in colour, WL-safe.
- DICOM **overlay planes** (graphics, group 60xx) → composited as a coloured diagram.
- 8-bit and 16-bit colour.
- Verified on the real 46382 files: series 21 (green/blue WO map), 22 (red TTP map),
  100/101 #6 (the Mean-Curve result table reappears). Grayscale series unchanged.

## 5. Limitations / remaining work

- **Advanced (VTK/MPR) viewer**: colour + overlay are implemented in the FAST 2D
  viewer (the default). The Advanced VTK 2D/MPR path builds a `vtkImageData`
  upstream and would need a parallel change (3-component image + overlay actor);
  scoped as a follow-up — not shipped here to avoid an unverifiable change to the
  guarded VTK render path.
- **Thumbnails** are generated server-side (PNG bytes from the PACS); colour
  thumbnails depend on the server rendering colour. Local colour-thumbnail
  generation is a separate follow-up.
- **Siemens MedCom Object Graphics** `(0029,1210)` (private vector OOG, can be
  full-colour) is not rendered — proprietary. The standard overlay plane (which
  carries the same chart here) is rendered instead.
- Overlays are 1-bit monochrome by the DICOM standard, so they render in one
  highlight colour, not full colour.
