# Stacking lag on patient 55387 — machine or app?

**Date:** 2026-08-23
**Question (owner):** *"check the stacking in 55387; there are some lag — check if it's
because of pc resource or the app"* (clarified: **55387 is the patient id**).
**Session analysed:** pid **90364**, 2026-08-23 14:28:45 → 15:39:45 (26,453 log lines).

---

## Verdict

**Both — and one of them is our bug.**

The app's stacking work is **not** the bottleneck: a frame costs a median of
**1.6 ms** and disk/decode/cache waits are **zero**. The lag the owner feels is
**the main thread not being scheduled**, and it has two causes:

1. **Ours (fixed).** `main.py` has always *asked* Windows for
   `ABOVE_NORMAL_PRIORITY_CLASS`. **The request never landed** — a ctypes typing
   defect made `SetPriorityClass` fail with `ERROR_INVALID_HANDLE` on **every
   launch** (19 launches in the retained logs, 19 failures, 0 successes). So the
   viewer competed for CPU on equal terms with everything else on the box.
2. **The machine.** This workstation is shared with a QEMU VM (42,470 CPU-s),
   Android Studio, Apache httpd, VS Code, Chrome, Proxifier, Grammarly, a VPN
   client and several Claude processes. It is not short of *capacity* — 10C/20T,
   64 GB with 27 GB free, disk queue 0 — it is short of *uncontended moments*.

A third, smaller factor: the app is being run **from source** (`python.exe
main.py`), not from the optimized frozen build.

### But the latency is not — 98 drag sessions

| metric | median | p90 | max |
|---|---|---|---|
| `ui_lag_max_ms` | **300.5** | 642.5 | 1160.3 |

**`event_p95` 84.5 ms against `handler_p95` 9.0 ms is the whole finding.** The
~75 ms gap is time between Qt receiving the input event and our handler being
allowed to start. Our handler, once it starts, is fast. Our paint is fast.

### Where the main thread actually was — 1,002 stall records, 66 with a stack

`gap_ms` median **163 ms**, p90 **422 ms**, max **2,846 ms**.

**45 of the 66 sampled stacks bottom out in `run_forever` with nothing below
it** — the main thread was sitting inside the Qt event loop, not executing our
Python. That is the signature of *waiting to be scheduled*, not of slow code.

Of the 21 samples that did catch app work, **none is on the stacking path**:
MPR open (5), voice save via `soundfile.write` (5), startup `setupUi` (2), app
close (1), three `stat` calls. In a session with 15,759 stack frames and 98
drags, the stall probe caught the stacking code **zero times**.

### The stalls are not on the disk

- seconds with foreground disk: 612
- seconds with a GUI stall: 668
- seconds with **both**: 215 (32 %)

The ten busiest disk seconds of the session recorded **0 stalls** in nine of
them and 1 in the tenth. Disk is not what the GUI is waiting for.

## The defect: the priority boost never worked

`main.py` (pre-fix):

```python
_k32 = ctypes.windll.kernel32
_hproc = _k32.GetCurrentProcess()
if _k32.SetPriorityClass(_hproc, _pri_class):
```

`GetCurrentProcess()` returns the pseudo-handle `(HANDLE)-1` ==
`0xFFFFFFFFFFFFFFFF`. Under ctypes' **default** `restype` of `c_int` that is
truncated to a 32-bit `-1`, and passing that on as an untyped argument makes the
x64 call hand a 32-bit value to an API that wants a 64-bit `HANDLE`. Measured on
this machine:

```
default restype  -> handle = -1                  -> SetPriorityClass = 0, err = 6
c_void_p restype -> handle = 0xffffffffffffffff  -> SetPriorityClass = 1, err = 0
```

`err 6` is `ERROR_INVALID_HANDLE`. The app logged it every single launch and
nobody read the line:

```
14:28:45  pid=90364  WARNING  [CPU_BUDGET] SetPriorityClass failed (err=6); using Windows default
```

**Retained logs: 19 launches, 19 failures, 0 successes.**

### The fix — three ctypes declarations

```python
_k32.GetCurrentProcess.restype = ctypes.c_void_p
_k32.SetPriorityClass.argtypes = [ctypes.c_void_p, ctypes.c_uint]
_k32.SetPriorityClass.restype = ctypes.c_int
_hproc = _k32.GetCurrentProcess()
```

Order matters: `restype` set *after* the call is a no-op, so the guard test pins
the ordering, not just the presence of the lines.

### Verified in the field, not only in a test

```
15:40:55  pid=47996  INFO  [CPU_BUDGET] Main process priority set to above_normal (class=0x8000)
```

and the live process reports `PriorityClass = AboveNormal`. **First success ever
recorded in these logs.**

## What to change

Ranked by effect per unit of risk.

1. **Done — the priority fix.** No configuration needed; it applies on next
   launch. Kill switch: `AIPACS_PRIORITY=normal`.
2. **Close the QEMU VM (and Android Studio) while reading.** 42,470 CPU-seconds
   of cumulative VM time is the single largest competitor on this box, and a VM
   is a *sustained* consumer, not a bursty one. This is the biggest remaining
   lever and it costs nothing to test: read one stack with the VM off and
   compare `ui_lag_max_ms`.
3. **Run the frozen build for clinical reading, not `python main.py`.** Source
   runs pay import and interpreter overhead the release build does not. This is
   a real difference but it is **not quantified here** — treat it as a
   hypothesis to measure, not a claim.
4. **Consider `AIPACS_PRIORITY=high`** only if 1–3 are not enough. The source
   comment's caution stands: HIGH can starve disk I/O and make downloads slower.

---

## What was deliberately NOT done

- **No change to the stacking path.** It is measurably fast (1.6 ms/frame, zero
  disk wait). Optimising it would be optimising the part that is already working.
- **No change to the throttle, cache, or prefetch.** Nothing in the data
  implicates them; `foreground_disk_reads` median is 0.
- **No logging change.** Logging was ruled out as a cause: `diagnostic_logging.py`
  routes every file handler behind a `QueueHandler`/`QueueListener`, so log
  writes do not happen on the GUI thread.
- **The `soundfile.write` stalls (5 samples, voice save) were not fixed.** They
  are real GUI-thread blocking, but they are on the voice-note path, not the
  stacking path, and the owner asked about stacking. Worth its own look.

---

## Honest limitations

- The `ui_lag_max_ms` numbers are **per drag maxima**. Typical frames are fine —
  `ui_lag_ms` across all 15,759 frames has a median of 8.9 ms. What the owner
  feels is not constant lag; it is roughly one ~300 ms hitch inside each drag.
- The priority fix **has not yet been measured against a post-fix reading
  session.** It is proven to apply (log line + live `PriorityClass`); its effect
  on `ui_lag_max_ms` is expected, not yet demonstrated. Re-run
  `stack_lag_55387_detail_2026_08_23.py` against a post-fix pid to close that.
- Priority is a *tie-breaker*, not extra capacity. If the VM is saturating cores,
  ABOVE_NORMAL helps the viewer win contests it was previously losing; it cannot
  create CPU that is not there. Item 2 above is not optional.

## Follow-up (same day): HIGH priority on deployed workstations

**Owner:** *"fix this in a way that, on other pc it use the high priority."*

"Other PC" needs a rule the app can evaluate at startup. The rule chosen is
**build type**, because it is exactly the discriminator that separates this
machine from every deployed one and needs no per-PC setup:

| Machine | Detected by | Default |
|---|---|---|
| Installed / frozen build (`AIPacs.exe`) | `aipacs_runtime.is_frozen()` | **HIGH** (`0x00000080`) |
| Running from source (`python main.py`) | same helper, returns `False` | **ABOVE_NORMAL** (`0x00008000`) |

`AIPACS_PRIORITY = normal | above_normal | high` still overrides both, and
`normal` remains the kill switch (it skips the call entirely). An
**unrecognised** value now falls back to the machine's own default rather than
to a hard-coded `0x00008000` — previously a typo on a clinical workstation
would have silently demoted it.

`is_frozen()` is the canonical helper and understands both PyInstaller
(`sys.frozen`) and Nuitka (`__compiled__` / `sys.__nuitka__`, normalised by the
bootstrap at the top of `main.py`). A failure in the probe degrades to the
**source** default, never to HIGH.

Verified on this machine: `is_frozen()` is `False`, so **nothing changes here**
— this box stays at ABOVE_NORMAL and keeps sharing CPU with the VM, the IDE and
the compiler. The success log line now records which default was used:

```
[CPU_BUDGET] Main process priority set to %s (class=0x%X, default=%s, frozen=%s)
```

### The HIGH caveat, and the second defect it exposed

The original source comment refused HIGH because *"it can starve disk I/O and
make downloads slower."* That concern is real, and the codebase already had a
mitigation designed for it: the DM download subprocess demotes **itself** to
`BELOW_NORMAL_PRIORITY_CLASS` so the viewer wins scroll contests.

**That demotion has the identical ctypes defect and has therefore never
applied.** `modules/download_manager/workers/download_process_entry.py:149`:

```python
_ctypes.windll.kernel32.SetPriorityClass(
    _ctypes.windll.kernel32.GetCurrentProcess(), _BELOW_NORMAL
)
```

No `restype`, no `argtypes`, **and the return value is not checked** — so unlike
`main.py` it never even logged a failure. The download subprocess has been
running at Normal all along.

The consequence is bigger than one missing demotion. The same file's v2.3.7
comment (lines 166–175) explains a measured priority inversion and states the
premise *"the viewer (ABOVE_NORMAL) blocks waiting on a lock held by an
IDLE-scheduled thread in the subprocess, producing the exact `event_p95` spikes
while `handler_p95` stays low pattern observed."* **That premise was false** —
the viewer was at Normal, not ABOVE_NORMAL — and the pattern it describes is
precisely what pid 90364 shows (`event_p95` 84.5 ms vs `handler_p95` 9.0 ms).
The intended priority separation has never existed at runtime: **both ends were
at Normal.**

**Not fixed here, deliberately.** Fixing it changes scheduling on the download
path, where this repo has *measured* harm from widening the gap
(`ui_lag_max 412 ms` vs `229 ms` under comparable load when the subprocess
dropped to IDLE). Viewer HIGH (13) against downloader BELOW_NORMAL (6) is a
**wider** gap than the ABOVE_NORMAL/IDLE pairing that was measured as harmful,
so this needs its own decision and its own measurement, not a silent fix
attached to this one.

**Until it is fixed and measured, treat `high` as untested against heavy
concurrent downloading.** Fall back with `AIPACS_PRIORITY=above_normal` on any
workstation where downloads regress after this change.

### Guards

`tests/code/system/test_cpu_budget_priority_boost.py` is now **23 guards**, of
which **16 fail pre-fix**. The build-type tests are **behavioural, not source
pins**: the resolution lines are lifted out of `main.py` by anchor and executed
against stubbed inputs, so they test what the shipped code actually decides.

Two guards were **re-pinned rather than deleted**, and both are recorded as
deliberate in the test file:

- `test_normal_escape_hatch_preserved` — the default argument moved from the
  literal `'above_normal'` to `_pri_default`. Same property, new spelling.
- `test_high_priority_class_is_not_the_default` →
  `test_high_is_the_default_only_for_installed_builds`. **The policy changed by
  request.** The guard is re-pinned to the new policy so that a later edit
  quietly making HIGH the default for source runs too is still caught.
