## 3. RETRACTION — the DICOMDIR hypothesis was wrong

**What I published on 2026-08-23:** our DICOMDIR's SERIES records carry only
`Modality, SeriesInstanceUID, SeriesNumber` (true — `modules/dicom_media/dicomdir.py`
builds with `pydicom.fileset.FileSet`, whose default SERIES recorder emits exactly
those three), **and I asserted that DCMTK's `dcmmkdir` includes `SeriesDescription`,
so cvi42 would see 75 nameless series.**

**That assertion is false.** Tested directly against a DICOMDIR inside cvi42's own
data store that cvi42 has evidently ingested:

```
…\cvi42\mri heart\previous\third 100\test 68 PHTN\export-060922-004225\DICOMDIR
Implementation      : 1.2.276.0.7230010.3.0.3.6.3 / OFFIS_DCMTK_363
SERIES record keys  : Modality, SeriesInstanceUID, SeriesNumber
SeriesDescription   : None
```

A genuine DCMTK-produced DICOMDIR carries **exactly the same three fields as
ours**. Our IMAGE records additionally carry `SpecificCharacterSet` — a superset,
not a loss. **Our DICOMDIR is not the problem, and no change to it is warranted.**

The supporting circumstantial claim was also overstated. Across the 34 cvi42
study folders, **33 have no DICOMDIR and 1 does** — so cvi42 plainly ingests both
shapes. "The working reference has no DICOMDIR" was true of that one folder and
is not a pattern.

## 4. The only remaining anomaly (recorded, not blamed)

`(0051,1014)` is written with VR **`UN`** in all 240 flow files. It is a
fingerprint of the server-side re-encode — our files are stamped
`ImplementationVersionName = PACS_SERVER_1.0`,
`ImplementationClassUID = 1.2.826.0.1.3680043.8.498.1` (the **pydicom** UID
root), so the server rewrites datasets rather than storing scanner bytes
verbatim. It is the only VR anomaly in the file, it is 12 bytes, and no flow
package is known to key on that tag. Not a plausible cause; kept on the record
because it is real evidence that a rewrite happens.
