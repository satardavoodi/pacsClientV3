# 46630 — Breast-MRI overlay annotations & mean-curve charts not rendered (FAST viewer)

**Date:** 2026-06-17
**Patient:** 46630 (MASOUMI^TINA), Siemens syngo MR, BREAST dynaVIEWS
**Study (MR):** `1.3.12.2.1107.5.2.46.174759.30000026061604302027000000090`
**Series:** 100, 101, 102, 103, 104, 105 (5 images each)
**Area:** FAST viewer decode/render only. **No VTK / MPR / geometry / slice-order change.**

## Symptom

In the AI-PACS workstation, for series 100–105:
- The first three (breast MR) slices display, but the **ROI annotation on slice 3 is missing**.
- The last two slices (device "mean-curve" charts) display as **solid black**.

A reference DICOM workstation renders the same downloaded files correctly (ROI
annotation + magenta enhancement-curve chart), so the files are valid and the
defect is in our decode/render pipeline.

## Investigation (forensic, real files)

Per-slice probe of all six series (uniform structure) — `pydicom` on the live `.venv`:

| Slice | SOP Class | ImageType | Photometric | Pixels | Overlay (6000,3000) |
|------|-----------|-----------|-------------|--------|---------------------|
| 1–3  | MR Image Storage | `…M\NORM\…\CSA RESAMPLED` | MONOCHROME2 416×396 | real image | **type G, 20592 B = 416·396/8** |
| 4–5  | Secondary Capture | `…OTHER\CSA BLACK IMAGE` (DerivationDesc=`MeanCurve`) | MONOCHROME2 512×512 | **all-zero** | **type G, 32768 B = 512·512/8** |

So this is the **same class as patient 46382**: the ROI annotation (slice 3) and
the mean-curve charts (slices 4–5, whose PixelData is entirely zero) live in a
**DICOM overlay plane `(6000,3000)`** ("Siemens MedCom Object Graphics"), not in
PixelData. No RGB / YBR / PALETTE photometric anywhere; `decode_color_for_display`
correctly returns `None` for every slice.

Running the existing shared fix functions on the real files produced correct masks:
`extract_overlay_mask` → 717 lit px (slice 3 annotation), 5546 (slice 4 chart),
11197 (slice 5 chart); rendered output matches the reference viewer (only the
highlight colour differs: green vs magenta).

## Root cause — the fix lived in the wrong FAST backend

The 46382 overlay/colour fix (commits `da681a9` + `1b6a2ed`) was wired into
`modules/viewer/fast/pydicom_2d_backend.py` — the **`lazy_backend`** (its
`get_frame()` composites overlays). But the **live FAST viewer** renders through a
**different** module:

```
qt_viewer_bridge → Lightweight2DPipeline (modules/viewer/fast/lightweight_2d_pipeline.py)
```

Runtime confirmation (download_diagnostics / app.log):
`active_backend=pydicom_qt` for series 100–105, with **zero `lazy_backend` decode
entries**. The lightweight pipeline builds its QImage directly in
`_render_frame_uncached` (decode → W/L → `_numpy_to_qimage_gray`) and **never
imported `dicom_overlay` / `dicom_color`**. So overlay planes were dropped and the
black SC frames rendered black — exactly the reported behaviour. The 46382 fix was
real and correct, but the GUI path for these series doesn't use that backend.

## Fix — composite overlays/colour in the active pipeline (reusing the shared modules)

`modules/viewer/fast/lightweight_2d_pipeline.py` only. No new decode logic — it now
calls the **same** proven `dicom_overlay` / `dicom_color` modules:

- New module helper `_dataset_has_dicom_extras(ds)` (overlay plane, or palette /
  embedded-palette / YBR on <3 samples).
- `_series_has_extras(idx)` — one-time per-series header probe (first/mid/last +
  current slice). Ordinary grayscale series resolve to `False` and pay nothing more.
- `_ensure_extras(idx, sm, arr)` — for extras series only, reads the dataset once
  per slice and caches the overlay mask + (palette) colour frame.
- `_render_frame_uncached` routes: colour frame → RGB; else windowed grayscale, and
  if an overlay mask is present it composites it in the highlight colour
  (`AIPACS_DICOM_OVERLAY_COLOR`, default green) onto an RGB frame. No-overlay
  grayscale stays `Format_Grayscale8`.
- Lazy-init (`_ensure_extras_state`) keeps `__new__`-built test doubles safe.

**Gating / safety:**
- Master switch `AIPACS_FAST_DICOM_EXTRAS` (default on); the overlay/colour modules
  keep their own `AIPACS_DICOM_OVERLAY` / `AIPACS_DICOM_COLOR` gates.
- With the gate off the render path is byte-identical to before.
- The hot grayscale path is untouched (no overlay → original `Grayscale8` build).
- True-RGB (`samples_per_pixel ≥ 3`) stays on the existing branch; only overlay
  compositing is added there.
- No change to decode of pixels, geometry, slice order, W/L, VTK, or MPR.

## Scope / remaining

- Drag-and-drop + scroll use the same `get_rendered_frame` path, so the fix applies
  there too.
- **Series thumbnails are server-rendered PNGs** today — a black-SC/overlay slice
  thumbnail is a server concern, unchanged here (same as the 46382 follow-up).
- The **Advanced (VTK) viewer** overlay/colour path is still not wired (out of
  scope; builds `vtkImageData` upstream). The FAST viewer is the default for these
  series.
- Other clinic PCs need the rebuilt 3.3.x installer to pick up the fix.

## Regression guard (future edits)

There are **two** FAST decode backends. The live GUI for opened series uses
`Lightweight2DPipeline` (`active_backend=pydicom_qt`), **not** `pydicom_2d_backend`
(`lazy_backend`). Any per-slice display behaviour (overlays, colour, LUTs) must be
applied in **`lightweight_2d_pipeline._render_frame_uncached`** to reach the screen.
