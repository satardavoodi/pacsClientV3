# Automatic Incremental Update System — Design + As-Built (2026-07-16)

Status: IMPLEMENTED (client + build + publish tooling); NEEDS live verify on a real
installed build (full check → notify → delta download → apply → restart cycle).
Owner: auto-update subsystem. Master-plan entry: OPT-38 (§9/§15).

## 0. Problem

Every release today requires building a full installer, transferring it to each
center, and reinstalling manually. There is no in-app update detection, no
notification, no incremental download, no rollback. Most of the 1.4 GB payload
(Qt/VTK DLLs) is identical between releases.

## 1. What already existed (the seam we extend — do NOT fork)

The repo already has a **manual** update system:

- `config/update_sources.json` — sources `[{id,type:"file"|"url",location,channel}]`,
  `active_source_id`; live copy in `%APPDATA%\AIPacs\config`; `sources[].location`
  blanked at build by `builder/config_sanitizer.py`.
- `update_feed.json` — generated by `builder/build_release.py::publish_update_bundle()`
  into `builder/output/updates/` (`core/` + `modules/` + feed). Core entry =
  `artifact_type:"installer"` (full installer download).
- Engine in `aipacs_runtime.py`: `load_update_sources` (:555), `load_update_feed`
  (:1088), `summarize_available_updates` (:1184), `compare_release_versions` (:849),
  `install_component_update` (:1443), `prepare_core_update_installer` (:1469),
  `launch_core_update_installer` (:1493), `updates_cache_root()` (:426) =
  `%LOCALAPPDATA%\AIPacs\updates`.
- Settings UI: `settings_ui/installation_module_settings.py` (Check Updates / Set
  Update Folder / Set Update URL / Apply Update).
- Gaps: manual-only (no startup check), core update = full installer, blocking
  urllib with no progress, no rollback, no restart helper, no hosting structure.

This design ADDS a delta layer on that seam. The full-installer path is preserved
as the fallback (user decision 2026-07-16: "Incremental + installer fallback").

## 2. User decisions (2026-07-16)

1. Website: **design it standalone / host-agnostic** — the update tree may be
   uploaded to **two sites** (primary + mirror) serving the same static files.
2. Apply mode: **incremental + full-installer fallback**.
3. Check policy: **startup (off-thread) + manual** in Settings.
4. Consent: **notify → user starts it**; nothing downloads without consent.
   `required` releases only nag more visibly.

## 3. Architecture

```
BUILD (dev machine)                         WEBSITE (static, 1-2 mirrors)
build_release.py                            updates/aipacs/stable/
  └─ publish_update_bundle()                  update_feed.json          ← extended core entry
       └─ tools/build/generate_update_          core/manifest-<v>.json  ← file-level manifest
          manifest.py                           core/notes-<v>.md
            walk stage/core (== {app} tree)     core/<installer>.exe    ← fallback
            sha256 every file                   modules/…               ← existing module pkgs
            content-addressed store             files/<h2>/<sha256>.gz  ← content-addressed store
tools/build/publish_update.py  ── sync ──►     (grows across releases; only new
                                                 hashes are ever added)

CLIENT (installed build)
main.py ──(flag-gated, delayed, off-thread)──► modules/auto_update/service.py
  check: try sources in order (active → rest) ─ summarize_available_updates()
  update_available ► ui.UpdateNotificationDialog (version, notes, required badge)
  user clicks Update ► client.UpdatePlanner/Downloader (QThread)
    fetch manifest → hash local tree (cached index) → diff → download only
    changed blobs → gunzip+sha256 verify → staging mirror tree
    (fallback: manifest missing / delta ≥ threshold → existing installer path)
  Restart & Install ► apply.py writes apply_plan.json + apply_update.ps1 +
    rollback_update.ps1, launches helper (elevated only if install root not
    writable), app exits via the normal clean-shutdown path
HELPER (PowerShell, outside the app)
  wait for PID exit → backup → copy staged files (retries) →
  on ANY failure: restore backup, log ROLLBACK, relaunch old exe →
  on success: stamp installation_profile app_version (best-effort), relaunch
NEXT BOOT
  service reconciles version (engine/version.json → runtime_profile app_version),
  writes boot-ok health marker, prunes staging + old backups (keep 2)
```

## 4. Formats

### 4.1 `update_feed.json` core entry — EXTENDED, backward-compatible

```json
"core": {
  "module_id": "core_app", "title": "AIPacs Core",
  "release_version": "3.5.4",
  "artifact_type": "installer",
  "artifact_path": "core/ai-pacs installer v3.5.4.exe",
  "sha256": "…", "available": true,
  "delta": {
    "manifest_path": "core/manifest-3.5.4.json",
    "manifest_sha256": "…",
    "files_base": "files/",
    "compression": "gzip"
  },
  "required": false,
  "min_version": "",
  "release_notes": "one-paragraph summary",
  "release_notes_path": "core/notes-3.5.4.md"
}
```

Old clients ignore the new keys (they only read artifact_*). New clients use
`delta` when present and verifiable, else the installer path.

### 4.2 `manifest-<version>.json` (file-level, paths in INSTALLED layout)

`stage/core/*` maps 1:1 to `{app}` (`AIPacs_Setup.iss` [Files] :124), so manifest
paths are exactly install-root-relative: `AIPacs.exe`, `engine/**`.

```json
{
  "format_version": 1, "app_name": "AIPacs", "version": "3.5.4",
  "generated_at_utc": "…", "layout": "install_root", "compression": "gzip",
  "file_count": 4211, "total_size": 1468006400,
  "files": [ {"path": "engine/PacsClient/….pyd", "size": 12345, "sha256": "…"} ]
}
```

### 4.3 Content-addressed store

`files/<sha256[:2]>/<sha256>.gz` — gzip of the RAW file; `sha256` is the hash of
the UNCOMPRESSED content (verified after gunzip). Publishing a new release adds
only blobs whose hash is new; unchanged DLLs are never re-uploaded or
re-downloaded. The store is plain files → works on any static host (the two
mirror sites just carry the same tree).

## 5. Hard rules (updater guardrails)

1. **The applier writes ONLY paths listed in the manifest, under the install
   root.** Path guard (generator AND client AND helper plan): relative only, no
   `..`, no absolute/drive paths, must start with an allow-listed payload root
   (`engine/`, `Qss/` — case-insensitive) or be a top-level file (`AIPacs.exe`),
   and NEVER match `user data/…` (2026-07-17: `Qss` added — the staged tree
   ships it beside `engine/`; `User Data` stays excluded by construction).
2. **Never touch center state**: `%APPDATA%\AIPacs\config\**` (all center
   settings: servers, socket, EchoMind, EagleEye/AI, reception/INO, offline
   cloud, identity, tokens), `<install>\User Data\**` (DB, DICOM, thumbnails,
   attachments, logs), `%LOCALAPPDATA%\AIPacs\user_data`, ProgramData profile
   (single exception: best-effort `app_version` stamp), module_packages.
   Config preservation is by construction — live config lives OUTSIDE the
   payload tree and the payload's `engine/config/*` are sanitized SEED templates
   only (create-if-missing seeding + `CONFIG_FAMILY_VERSIONS` key-merge remain
   the only channels that touch user config).
3. **Never block the GUI thread** — check + hash + download run on worker
   threads; UI only via signals (OPT-22/23 lesson).
4. **Nothing downloads or installs without user consent** (decision #4).
5. **The helper never kills the app** — it waits for clean exit (timeout →
   abort+log, exit unchanged). App exit uses the existing clean-shutdown path.
6. **Rollback on apply failure is automatic** (restore backed-up files, relaunch
   old exe). Backups for the last 2 versions persist under
   `%LOCALAPPDATA%\AIPacs\updates\backup\<version>\` with `rollback_update.ps1`.
7. **Every step logs**: app side → `user_data/logs/auto_update.log`; helper →
   `%LOCALAPPDATA%\AIPacs\updates\logs\apply-<v>-<ts>.log`.
8. Delta gen failure at build must NEVER fail the release build (try/except →
   feed simply carries no `delta`, clients fall back to installer).
9. v1 applies adds/replacements only — **no deletions** (a stale extra file is
   logged, not deleted). Revisit after live soak.

## 7. Flags / config

- `AIPACS_AUTO_UPDATE_CHECK` — default ON when frozen, OFF in dev (=1 forces on,
  =0 kills). `AIPACS_UPDATE_CHECK_DELAY_S` (default 20).
- `AIPACS_UPDATE_DELTA` (default on; =0 → installer path only),
  `AIPACS_UPDATE_INSTALLER_FALLBACK` (default on).
- `update_sources.json` tolerant new keys (no migration needed — read with
  defaults): `auto_check_on_startup` (default true). Multiple sources = mirror
  failover, active source first.

## 8. Version identity

`pyproject.toml` stays the single source of truth at build. The build stamps
`engine/version.json` (`{"app_name","version","built_at_utc"}`) into the payload,
so a DELTA update carries its own version identity. On boot the service
reconciles: if `engine/version.json` ≠ `current_app_version()`, stamp
`runtime_profile.app_version` (which `current_app_version()` reads first). The
helper also best-effort updates ProgramData `installation_profile.json`.

## 9. Fallback + failure matrix

| Failure | Behavior |
|---|---|
| Source 1 unreachable | try next source (mirror), else silent log (startup) / message (manual) |
| Feed has no `delta` | full-installer path (existing, preserved) |
| Manifest hash mismatch / blob hash mismatch | abort download, keep app untouched, log; retry re-downloads only bad blobs |
| Delta size ≥ threshold (default 60% of installer, when installer size known) | prefer installer fallback |
| App fails to exit within 90 s | helper aborts, changes NOT applied, old app keeps running |
| Any copy fails during apply | automatic restore of backed-up files + relaunch old exe (ROLLBACK logged) |
| New version fails to boot | backup for the previous version persists + `rollback_update.ps1`; boot-ok marker absent is visible in logs (auto-boot-watchdog deliberately NOT in v1) |

## 10. Live-verify checklist (clinical lane, pending)

1. Build vN, install on a test PC; build vN+1, publish to a local folder source
   AND an HTTPS source. 2. Startup notification appears (≤ ~30 s after login,
   GUI never blocks). 3. Delta download shows progress; only changed files
   fetched (KPI: bytes vs installer size). 4. Apply → app restarts as vN+1;
   servers/EchoMind/EagleEye/reception/offline-cloud settings + credentials all
   intact; DB/patients untouched. 5. Kill the copy mid-apply (rename a locked
   file) → rollback relaunches vN. 6. `update_health.json` boot-ok written;
   backups pruned to 2. 7. Settings manual check + installer fallback both work.
