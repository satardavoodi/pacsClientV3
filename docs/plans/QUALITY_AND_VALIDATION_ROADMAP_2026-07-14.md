## 0. Phase Q0 — REPAIR THE INSTRUMENT — **COMPLETE (2026-07-14)**

The instrument is fixed. Before/after, measured:

| | Before Q0 | After Q0 |
|---|---|---|
| Full `tests/code` run | **hung at 56 %, never finished** | **completes in ~85 s** (`-n auto`) |
| Suite exit status | RED by default (~80 permanent failures) | **exits 0 (green)**, deterministic across repeated runs |
| Regression signal | none — answered by hand with `git stash` A/B | **any new red is a real regression** |
| Tooling | `pytest` only | + `pytest-timeout`, `-xdist`, `-cov`, `-rerunfailures`, `hypothesis` |
| Coverage number | unknown | **baseline 26 %** (190,594 stmts; `PacsClient`+`modules`) |

**What was actually wrong (all measured, none assumed):**
1. **The hang** was ONE test — `tests/code/builder/test_plugin_package_builder.py` — spawning a
   REAL build subprocess that never returned. Marked `build`; excluded from the fast lane
   (`-m build` runs it deliberately). `--timeout=120` makes any future hang *name itself* instead
   of killing the run.
2. **The 80 reds** were **test debt, not product bugs** — stale test doubles (an OAuth fake whose
   signature drifted → 8 identity failures), baseline/drift pins not updated after product changes,
   golden pixel-hash drift, and a handful of genuinely flaky tests. Categorised and driven to zero:
   - **Fixed at source** where cheap: the OAuth-fake signature (`require_embedded`); a wall-clock
     timing test rewritten to assert on **observed concurrency** (`test_reception_fetch_speed`).
   - **Quarantined** (the rest) via an explicit, self-cleaning registry (below).
   - **Isolated**: real-network tests (`test_gapgpt_connection`) marked `live`; parallel-unsafe
     Qt-threading tests (`test_manager_queue`) marked `flaky_parallel` and run serially.
   - **Absorbed**: a residual cluster of viewer-interaction *timing* tests (B34/B41) via
     `--reruns 2` — pass-on-retry is flaky, fail-all-attempts is a real regression.

**The quarantine is a self-cleaning DEBT REGISTER, not an amnesty** (`tests/quarantine.py`
auto-generated by `tools/dev/build_quarantine.py`; `tests/quarantine_manual.py` hand-maintained;
applied as `xfail(strict=True)` in `tests/conftest.py`). `strict=True` means a quarantined test
that **starts passing FAILS the suite** — so the list cannot rot, and it shrinks as the debt is
paid. Regenerate anytime; `--check` flags any new failure not already listed. **79 tests are
quarantined today; every one is a tracked bug to burn down.**

**The one command** (`run_test.ps1`): fast lane (`-n auto`, reruns, excludes build/slow/live/
flaky_parallel) + a serial pass for the `flaky_parallel` set. `.\run_test.ps1 -Fast` for the
quickest gate; `-Cov` for coverage; `-Build` / `-Live` for the heavy lanes.

**Lanes** (`pyproject.toml`): `build`, `slow`, `live`, `flaky_parallel`, `property` — all excluded
from the default fast lane, each runnable with `-m <marker>`.

**Honest caveats (the burn-down list):**
- Coverage is **26 %** — a floor to raise deliberately, NOT a target to game (see §6).
- ~79 quarantined + the `flaky_parallel` set + a viewer-interaction timing cluster behind
  `--reruns 3 --reruns-delay 2` are all **real test-quality debt**. Green today means "no *new*
  regressions", not "every test is sound". A large latent-flakiness tail was HIDDEN by the old
  80-red state and is now visible — that visibility is the point, and burning it down is L3/L0 work.
- `loadscope`/`loadgroup` xdist distributions were tried for the Qt-state flakiness and **rejected**
  (>4 min; they pin the 157-file viewer suite to one worker). The fast lane stays on `--dist load`.
- **Quarantine is NON-STRICT xfail** — `strict=True` was tried and rejected: a *timing-flaky*
  quarantined test that happens to pass triggers a strict-XPASS suite failure (red for the opposite
  reason). Burn-down is enforced by the explicit audit `build_quarantine.py --check` (reports new
  regressions AND now-passing entries), not by a per-run strict-xpass.
- **`flaky_parallel` vs quarantine — the rule learned here:** a test that FAILS in the *call phase*
  can be quarantined (xfail catches it). A test whose failure is *out-of-call-phase* (a leaked Qt
  worker thread corrupting the next test's setup/teardown — `test_manager_queue`) or that only
  flakes under CPU contention (`test_b34_interaction_aware_policy`) canNOT be reliably quarantined;
  it must be `flaky_parallel` (serial lane) instead.

## 0b. Phase Q2 — STATEFUL identity model — **DONE (2026-07-14)**, first L3 discovery test

The single highest-value new test from §3-L3 is built and proven: a hypothesis `RuleBasedStateMachine`
(`tests/code/viewer/test_series_ref_stateful.py`, marked `property`) that drives the `SeriesRef`
authority through **arbitrary sequences** of study-merges and series-adds — with colliding series
numbers across studies — and asserts, in every reachable state: I1 every display key resolves to ITS
OWN study; I2 SLOT STABILITY (a key never changes study over time); I3 keys + series_uids are unique;
I4 the slot-fallback path agrees with the table; I5 synthetic 9xxxxx numbers stay plain primary keys.

**It has teeth — proven.** Injecting the exact historical 2026-06-20 defect (re-sorting slot order on
merge) into a throwaway subclass, the machine caught it and shrank it to a minimal reproducer:
`key 1000001 changed identity: was STUDY_2, now STUDY_1`. That is the order-dependent identity-bug
class (48912 / 49836 / 50238 / the 2026-06-20 slot-shift) that **no example-based test in the suite
detects**, found automatically. Runs in its own lane (`run_test.ps1 -Property`, or `pytest -m
property`) — kept OUT of the parallel fast lane because a CPU-heavy hypothesis run starves the
timing-sensitive viewer tests.

## 0c. Phase Q3 (start) — PROPERTY-BASED fuzz of the ingestion boundary — **DONE (2026-07-14)**

`tests/code/network/test_series_identity_property.py` (marked `property`) fuzzes
`modules/network/series_identity.py` — the exact choke point where **OPT-25** lived (the literal
`"None"` that `int()`-ed a whole study to death). It generates arbitrary server payloads (ints,
floats, NaN/inf, bytes, booleans, the "absent" spellings, zero-padded and float-as-text numbers,
unicode junk) and proves: P1 `parse_series_number` never raises and returns int-or-None; P2 the
normalizer never raises; P3 every series ends up with a USABLE number (the OPT-25 guarantee); P4
synthetic numbers stay in the reserved band and below the 1e6 offset threshold (C2); P5 no
synthetic collides and normalize introduces no NEW collision; P6 healthy data is byte-identical
(C3); P7 deterministic. **Teeth confirmed:** the pre-OPT-25 naive `int(str(v or 0))` parser raises
`ValueError` on the fuzzed `"None"` — precisely what P1 catches.

**The fuzzer earned its keep on the FIRST run** — it surfaced, in ~4 s, that the normalizer does
NOT deduplicate *duplicate real SeriesNumbers* from a server (two series both numbered `3` within
one study are both kept, byte-identical). That is a distinct, server-data-quality concern from
OPT-25 (missing numbers) and could feed the same folder/offset-key collision class as the
multi-study bugs (`SOURCE_PATH/<study>/<number>/`). It is captured as an explicit
`test_duplicate_REAL_numbers_from_server_are_preserved_not_deduped` and flagged as a **follow-up
candidate** (a potential new OPT item) — not silently swept under the test. This is exactly what
L3 is for: the technique found a latent edge case before a user did.

**Next in Q3 (not yet done):** fault injection (kill the socket mid-request; deliver a partial
download; make a study grow at T+5 min) and event-loop interleaving fuzz for the `clear_table`
re-entrancy class (OPT-29). Those need small harnesses; the pure boundary fuzz above was the
cheapest highest-value first cut.

## 2. The only diagnostic that matters: would our tests have caught the last 10 bugs?

Every bug below reached a **user**. For each, the honest answer to *"which technique would have
caught it before the user did?"*

| # | Bug | Class | Would existing tests catch it? | Technique that WOULD |
|---|---|---|---|---|
| OPT-25 | `int("None")` on a server field killed a whole study | **Malformed external input** | ❌ | **Property-based / fuzz at the ingestion boundary** |
| OPT-20 | Render gate compared a series **NUMBER** to a list **INDEX** | Type confusion | ❌ | **Typed value object + static typing**; metamorphic ("a series must render regardless of key magnitude") |
| OPT-20/3 | Study-blind name+count dedup dropped a distinct series | Multi-study data shape | ❌ | **Model-based scenario generation** (2 studies sharing a series name) |
| OPT-26 | A secondary load repointed the TAB's study path | **Order-dependent state** | ❌ | **Stateful/model-based testing** (sequences of loads) |
| 50238 | A primary load inherited the SECONDARY study's `study_pk` | **Order-dependent state** | ❌ | Same — the sequence *"load secondary → load primary"* |
| OPT-36 | Drop abandoned → previous image; fake `ViewportLoadSucceeded` | **Temporal invariant** | ❌ | **Invariant/temporal property** + **fault injection** (slow download) |
| OPT-37 | 5-min TTL blinded the change detector | **Time-dependent** | ❌ | **Simulated clock** + fault injection (server grows at T+5 min) |
| OPT-29 | `clear_table` native access violation | **Concurrency / re-entrancy** | ❌ | **Event-loop interleaving stress/fuzz** |
| OPT-28 | Stale pooled socket handed out as healthy | **Network fault** | ❌ | **Chaos / fault injection** (kill connection mid-request) |
| OPT-22/23/27 | 21 s / 55 s GUI-thread freezes | **Blocking on GUI thread** | ❌ | **Main-thread stall assertion as a test gate** (we already *log* it) |

**Score: 0 / 10.** Not one of them was catchable by the 566 files we have. That is not a failure of
effort — it is a failure of *technique coverage*. Our tests are almost entirely **example-based unit
tests and source-pins**: excellent at preventing a *known* bug from returning (and they have done
that well), useless at *discovering* an unknown one.

**The bugs cluster into five classes, and four techniques cover all of them:**

1. **Property-based testing** → malformed input, parsing, pure decisions.
2. **Stateful / model-based testing** → the entire multi-study identity family (the #1 recurring class).
3. **Fault & chaos injection** → network, partial download, slow disk, clock.
4. **Log-invariant scenario testing** → GUI freezes, temporal invariants, "no wrong image" — using the
   markers we *already emit* (`[IDENTITY-GATE]`, `[SERIESREF-SHADOW]`, `[MAIN_THREAD_STALL]`,
   `ViewportLoad*`) as **test oracles**, driven end-to-end by the **control MCP**.

Technique 4 is the biggest win and the cheapest, because both halves already exist and have never
been connected: **the MCP can drive the app, and the app already logs the invariants.** All that is
missing is a runner that asserts on them.

## 3. The five lanes

### L0 — REPAIR THE INSTRUMENT *(blocking; nothing else counts until this is done)*
1. **Install the missing tooling:** `pytest-timeout` (kill the hang), `pytest-xdist` (parallel),
   `pytest-cov`, `hypothesis`, `pytest-qt`, `pytest-randomly` (order-dependence detector).
2. **Find and fix the hang** (the run dies at ~56 % of `tests/code`). `--timeout=60` will name it.
3. **Get the suite GREEN — zero permanently-failing tests.** Each of the ~68 reds is either
   *fixed*, or *quarantined* with an explicit `@pytest.mark.xfail(reason=..., strict=True)` **and a
   tracking item**. A red suite has no signal. This is the single highest-value quality action
   available and it is pure cleanup — no product risk.
4. **Baseline coverage** (a number, not a target yet) and publish it per top-level package.
5. **One command:** `run_test.ps1` → full suite, parallel, green, < 3 min.

**Acceptance:** `pytest tests/code -n auto` exits **0**, in under 3 minutes, on a clean checkout.

### L1 — REGRESSION LANE *(routine, automated, every change)*
- **Tier 1 — pre-commit (< 30 s):** the pure/unit subset + all source-pins. Runs on every edit.
- **Tier 2 — pre-merge (< 3 min):** full `tests/code`, parallel, **must be green**.
- **Tier 3 — nightly (< 30 min):** Tier 2 + property-based (higher example counts) + the offscreen
  Qt lane + mutation testing on the *pure* authorities (`series_ref.py`, `patient_study_set.py`,
  `series_identity.py`, `patient_load_lifecycle.py`).
- **Golden-file / snapshot tests** for geometry + decode: a small fixture set of real studies (CT,
  MR, DX, US cine, multi-frame, DICOMized document, a multi-study patient, a missing-`SeriesNumber`
  device) with checksummed expected slice order, orientation, spacing, WL. **This is the clinical
  safety net that does not exist today.**

### L2 — LIVE / CLINICAL LANE *(the real GUI, scripted)*
This is what the **control MCP** was built for and has barely been used.

- **Scenario scripts** (`tools/testing/scenarios/*.yaml`) driving `aipacs_control_mcp`:
  `open_patient → drag_series → switch_layout → open_mpr → close` etc.
- **Log-invariant assertions** after every scenario — the oracle set (see §4).
- **The V-1…V-5 verification debt** from master plan §10 becomes **scenario scripts**, not a manual
  checklist. Once written, re-running them is free.
- **Soak:** `kpi_soak_run.py` for 60–90 min across many patients; assert no stall > 1 s, no leak, no
  native fault, no wrong-study skip.

**Cadence:** every release candidate; plus any change touching the viewer/identity/DM.

### L3 — EDGE-CASE DISCOVERY *(the answer to "routine bugs are rare; the remaining ones are exotic")*
This is the lane that finds bugs **before** users do.

| Technique | Target | Concretely |
|---|---|---|
| **Property-based** (`hypothesis`) | Ingestion boundaries + pure decisions | Generate arbitrary server payloads (missing/`"None"`/`""`/`"02"`/huge/negative `SeriesNumber`, absent `SeriesInstanceUID`, duplicate UIDs across studies) → assert `parse_series_number` never raises, `build_series_ref_table` never collides, synthetic numbers stay in-band. **This finds OPT-25 in seconds.** |
| **Stateful / model-based** (`RuleBasedStateMachine`) | **The multi-study identity family** | Model = {studies, series, viewports}. Rules = load/drag/switch/merge-previous-exam/download-completes. **Invariant: the viewport displays the series it was asked for, and never another study's.** This is the technique that would have caught 48912, 49836, 50238 **and** OPT-36 — the whole recurring class. **Highest-value single item in this roadmap.** |
| **Fault injection** | Network, disk, clock | Kill the socket mid-request; deliver a partial download; make a study grow 5 min after first view; slow the disk. Drives OPT-28/36/37 classes. |
| **Concurrency / interleaving fuzz** | Qt event loop | Randomly interleave search + status-refresh + pin-overlay + DM callbacks; assert no native fault, no re-entrancy. Drives OPT-29. |
| **Metamorphic** | Viewer | *"Displaying series X must be independent of the display-key magnitude, the order studies were merged, and which sibling was viewed before."* Cheap to state, brutal at finding identity bugs. |
| **Mutation testing** | The pure authorities only | Are our guard tests actually load-bearing? Run on `series_ref.py` etc. Not on the whole codebase — too slow, low value. |

### L4 — PERFORMANCE LANE *(regression gates, not one-off measurements)*
- We already have the KPI catalog + `kpi_session_report.py`. What is missing is a **gate**.
- **Assert budgets in the scenario runs**, from the logs we already emit:
  - `[MAIN_THREAD_STALL]` — **zero stalls > 1 000 ms during use** (this is the invariant that OPT-22/23/27 each violated for 20–55 s).
  - TTFI p50 ≤ 25 ms, decode p50 ≤ 6 ms (§13 baseline).
  - Patient-list search: client-side overhead ≤ 50 ms (server time reported separately — OPT-32 is server-side).
- **Fail the run on regression**, with the offending stack from the stall sampler. Performance work
  then becomes *"keep the gate green"*, not *"periodically go hunting"*.

### L5 — ARCHITECTURE / CONTINUOUS IMPROVEMENT
Priorities are already set in master-plan §10/§17 (verify → OPT-35 P3–P5 → flag debt → GUI-thread
offenders → OPT-04 re-scoped). What this roadmap adds:
- **Typed value objects at every boundary** (`SeriesRef` is the template) + **incremental `mypy`** on
  the pure authorities. The OPT-20 number-vs-index bug is *impossible* under a type checker.
- **Flag budget:** every new flag needs a **retirement condition** written at birth. Nine flags for
  one question is what forced the 07-14 reassessment.
- **Every production invariant gets a log marker AND a test oracle.** Today `[SERIESREF-SHADOW]` is a
  production oracle with no automated consumer. Close that loop.

## 5. Sequenced plan

**Phase Q0 — Repair the instrument (1–2 days, zero product risk).** L0 items 1–5. *Nothing else
starts until `pytest tests/code -n auto` is green in < 3 min.*

**Phase Q1 — Close the loop the MCP was built for (3–5 days).**
1. Scenario runner: MCP drives the app → scenario YAML → **assert the §4 oracle set** → pass/fail.
2. Encode **V-1…V-5** (master-plan §10) as the first five scenarios. This simultaneously **pays off
   the verification debt** and creates the permanent live-regression lane. *Two birds.*

**Phase Q2 — Stateful model of the multi-study viewer (1 week).** The single highest-value new test.
Would have caught 4 of the last 10 bugs. Start it the moment Q0 is green — it does not depend on Q1.

**Phase Q3 — Property-based at the boundaries + fault injection (1 week).** Server payloads, socket
faults, partial downloads, clock.

**Phase Q4 — Perf gates + golden geometry fixtures (ongoing).** Turn the KPI catalog into a
pass/fail gate; build the fixture study set.

**Then, and only then, resume feature/optimization work** with a green, fast, meaningful suite behind
every change.

## 6. What NOT to do

- **Do not chase a coverage percentage.** Coverage tells you what was *executed*, not what was
  *verified*. Our 566 files already execute a lot and caught none of the last 10 bugs.
- **Do not add more example-based unit tests for the identity path.** We have those. They pin known
  bugs. They do not find new ones. Build the state machine instead.
- **Do not mutation-test the whole codebase.** Pure authorities only.
- **Do not write GUI tests that click pixels.** Drive the app through the **MCP command surface**
  (T1 fidelity: it runs the real production code paths) and assert on **logs**, not screenshots.
- **Do not let the suite go red again.** A red suite is a broken instrument, and a broken instrument
  is worse than none — it produces false confidence.
